## 一、六个灵魂拷问

### Q1：既然有 Figma / Webflow / Illustrator，为什么还要做这个？

因为三者都不解决这件事：

| 产品          | 它能做        | 它做不到                                                                        |
| ----------- | ---------- | --------------------------------------------------------------------------- |
| Illustrator | 矢量编辑极致     | 产出是 `.ai`，不是 HTML；导出的 HTML 是垃圾代码                                            |
| Figma       | UI 设计 + 协作 | 产出是 `.fig` 私有格式，代码是"翻译"出来的（Dev Mode 之后好些，但仍非一等公民）；离线重客户端体验差；不产出可维护的 HTML 文档 |
| Webflow     | 产出干净 HTML  | 云端、订阅制、必须联网、不能离线、不能本地文件、Agent 无法本地批量操作                                      |
| 各类 AI 网页生成器 | 一句话出页面     | 用户改不了细节，改一个像素要重新生成整页                                                        |

**空位**：一个**本地、离线、矢量级精度、产出就是干净 HTML 源文件、Agent 可程序化读写**的编辑器。

这是"AI 时代静态网页生产"的中间层：**Agent 出草稿 → 人类用画矢量图的方式精修 → HTML 回到 Agent 继续迭代**。

### Q2：为什么必须用 HTML 当"矢量格式"，而不是自己定义格式再导出 HTML？

因为往返（round-trip）会烂。任何"自有格式 → 导出 HTML"的方案，第二次导入就废了——Figma/Sketch 都是这么烂的。

**只有让 HTML 本身就是源格式**，才能真正做到：
- Agent 写 HTML → 用户打开编辑 → 用户保存 → Agent 继续改（无限循环）
- git 友好：文本 diff，能 code review，能 merge
- 永不锁定：用户删掉本软件，HTML 还在

代价是：CSS 表达能力比矢量格式弱/怪（比如多重描边、混合模式、任意路径填充）。这是**必须接受的代价**，用"CSS 白名单 + Fallback 冻结块"来兜（见 04、05）。

### Q3："像 Adobe Illustrator"到底像到什么程度？

分三级，本项目取 **L2，个别处到 L3**：

| 级别 | 含义 | 举例 |
|---|---|---|
| L1 外观像 | 图标、深色主题、面板名字一样 | 90% 的"国产替代"软件止步于此，一上手就废 |
| **L2 肌肉记忆像** | 快捷键、鼠标修饰键、操作顺序、术语一致 | Alt 拖动=复制、空格=抓手、Cmd+D=再次变换、双击进隔离 |
| L3 行为细节像 | 吸附策略、手柄反馈、智能参考线触发时机、钢笔手柄的 Alt 断开 | 决定"像不像"的最后一公里 |

**判定标准**：让一个用了 5 年 AI 的人不看文档，能完成"画矩形 → 改渐变 → 编组 → 对齐 → 导出 @2x"。做不到就是没做到 L2。

### Q4：Vulkan 渲染器是刚需还是自嗨？

刚需，但**刚需的理由和你想的可能不一样**：

真正的性能瓶颈不是"画 10 万个矩形"（那是 benchmark 数字），而是：
1. **交互延迟**：拖动一个对象时，整帧必须在 16ms 内重绘完，否则手感就"黏"
2. **缩放/平移流畅度**：大文档下这是最常做、最容易卡的操作
3. **导出吞吐**：批量导出 50 个画板 @3x，CPU 软渲要几分钟，GPU 几十秒
4. **UI 与画布同帧合成**：如果用 Qt/WebView，UI 与画布两个 GPU 上下文，撕裂和额外拷贝不可避免

Vulkan（经 wgpu）同时解决以上四点，且能让 UI（egui）与画布共享同一个 wgpu device。

**但不要为 Vulkan 而 Vulkan**：用 wgpu 而不是裸 Vulkan API（见 ADR-002），保留 Metal/DX12 回退，核显/无独显机器降级到兼容模式而不是崩溃。

### Q5：为什么要合并 WPI？它和主程序不是一个语言（Python vs Rust）？

因为导出"像素真值"这件事，重写一遍是纯亏：

- WPI 已经解决了最难的部分：静态服务启动、Playwright 驱动系统 Chrome/Edge、整页测量、**reveal-on-scroll 动画展开**、**有限动画冻结**、超长页 PDF 分页、GIF 调色板、MP4 编码
- 这些是"浏览器行为的经验知识"，不是代码量问题，重写必踩坑
- 反过来，Vulkan 原生导出也需要（离线、快速、无浏览器依赖），二者**互补而非替代**

跨语言用「进程 / 常驻 sidecar」解决（见 07 篇），不引入 PyO3 这种会把构建复杂度翻倍的方案。

**结论**：v0.5 之前用 WPI CLI 进程调用（零改动 WPI），v0.6 起改为常驻 sidecar 复用浏览器实例（省掉每次 3-5 秒冷启动），并给 WPI 提 3 个参数（区域裁剪 / 画板定位 / JSON 输出）。

### Q6：一个人（+Agent）做得完吗？

做得完，但必须承认这是一条 **12-18 个月的长期项目**，且必须严格按 11 篇的里程碑推进，**每版都要能跑起来给人看**。

最大的风险不是技术，是**范围膨胀**。因此本篇第五节列出明确的"不做清单"，任何新想法先进该清单排队，不得插队。

## 二、产品定义

**Vellum Bench**：本地运行的桌面应用，用 Illustrator 的操作方式编辑标准 HTML/CSS 静态页面，编辑态由 Vulkan 实时渲染，产物是干净的 HTML 源文件，可被 Agent 通过 CLI / MCP / 文件监听读写，并能将页面导出为图片、PDF、GIF、MP4。

### 用户与场景

| 用户 | 场景 | 关键诉求 |
|---|---|---|
| **不懂代码的设计 / 运营**（主力） | Agent 生成了一个落地页，想改标题位置、换个配色、加个按钮 | 不用写代码、不用懂 HTML、改完还是标准网页 |
| **Agent 工程师** | 批量生成/修改 100 个页面；需要结构化地定位元素 | 稳定 id、patch 协议、可脚本化 |
| **WPI 存量用户** | 要把网页导出成图/PDF/GIF/MP4 | 编辑 + 导出一条龙，不用两个软件倒腾 |
| 前端开发者（次要） | 快速起静态页原型，导出可用代码 | 代码质量、可维护、无框架绑架 |

### 典型闭环（产品的灵魂场景）

```
1. 用户：「帮我做一个咖啡品牌的落地页」→ Agent 生成 index.html + style.css
2. 用户：Vellum Bench 打开该文件 → 看到画板、图层、元素（AI 式界面）
3. 用户：像在 AI 里一样，把主标题往左挪 20px、换渐变、加一个按钮编组
4. 用户：保存 → HTML 更新（干净、可读、可 diff）
5. 用户：导出 → Hero 画板 @2x PNG + 全页 PDF + 一段滚动动画 GIF
6. 用户：「把 CTA 按钮改成绿色」→ Agent 读取最新 HTML → 精准 patch → 用户端热重载
```

## 四、设计原则（写代码时用来做取舍）

1. **源文件第一**：任何功能不得破坏"输出是干净可读 HTML"这条底线。
2. **肌肉记忆优先于好看**：当"更现代的交互"与"和 AI 一致"冲突时，选和 AI 一致，另提供开关。
3. **显式优于隐式**：编辑器产生的效果，必须能在 HTML 里找到对应的、人类可读的表达。不要出现"只有本软件能解释"的黑魔法属性。
4. **降级不崩**：不支持的 CSS → 冻结为不可编辑块（可见、可移动、可删），而不是解析失败或渲染错乱。
5. **性能是可感知功能**：拖动不跟手 = 功能缺失，不是"优化项"。
6. **Agent 能做的，用户也能做；用户能做的，Agent 也能做**（命令模式天然满足）。

## 五、明确的"不做"清单（v1.0 之前）

> 每一条都是真实的诱惑。写在这里是为了在被诱惑时能引用。

- ❌ **不执行 JavaScript**：不做 JS 运行时。动画用声明式关键帧子集（转成 CSS animation）。
- ❌ **不做完整 CSS 引擎**：不追求 Chrome 级 CSS 覆盖，用白名单 + 冻结块。
- ❌ **不做后端/CMS/托管/发布**：只生成本地文件，发布交给用户或别的工具。
- ❌ **不做多人实时协作**：v3 再评估（CRDT 会污染文档模型设计，过早引入代价极高）。
- ❌ **不做 Figma 式的自动布局全家桶**：v0.7 只做 flex 基础 + 断点。
- ❌ **不做移动端/触控优先**：v3 再说，桌面鼠标键盘是主场。
- ❌ **不做插件市场 / 模板商城 / 账号体系**：v2 之后再考虑。
- ❌ **不接第三方大模型 API**：需要 AI 能力时由外部 Agent 通过协议驱动（与既有偏好一致：不给自己接外部 API）。

## 六、成功指标

### v1.0 的门槛（不达标不算 1.0）

| 维度 | 指标 |
|---|---|
| 迁移成本 | AI 用户不看文档完成 5 项基础任务（画/改/编组/对齐/导出）成功率 ≥ 80% |
| 保真 | 自绘渲染 vs Chromium 渲染，在**白名单 CSS 覆盖的场景**下像素差异 ≤ 1px 偏差（由校对视图自动比对） |
| 性能 | 5 万对象文档：平移/缩放 ≥ 60fps；拖拽单对象重绘 ≤ 8ms；冷启动 ≤ 1.5s |
| 代码质量 | 输出 HTML 通过 W3C 校验；无内联样式污染（除用户显式开启）；`prettier` 格式化后与输出 diff 为空 |
| 往返 | 100 个真实网页样本：导入 → 不编辑 → 保存，字节级等价于原文件（除格式化）比例 ≥ 95% |
| Agent | Agent 通过 CLI 完成"改 5 个元素 + 导出 3 个画板"成功率 100%，平均往返 < 3s |

### 北极星指标

**"被保存并再次被打开的 HTML 文档数"** —— 说明它真的成了源文件，而不是一次性玩具。

## 七、MVP 的最小定义（0→1 的终点线）

能完成下面这条完整链路，就算 0→1 成功：

1. 新建文档 → 有一个 1440×900 画板
2. 用**矩形工具(M)** 画 3 个矩形、**文字工具(T)** 写 2 段文字、导入 1 张图片
3. 用 **V** 选中 → 拖动 → **Alt+拖动**复制 → **Shift** 约束 → **Cmd+D** 再次变换
4. 编组(**Cmd+G**) → 对齐(**Ctrl+Shift+C/V**) → 图层面板改名字
5. 属性面板改：填充渐变、描边 2px、圆角 8px、不透明度 80%
6. **Cmd+S** 保存 → 得到 `index.html` + `styles/main.css`（人可读，浏览器打开视觉一致）
7. 导出：Hero 画板 @2x PNG、整页 PDF、HTML 打包 zip
8. Agent 通过 CLI：`find "主标题" → set_text → set_style → export` 全流程跑通

**做不到的部分，必须明确告诉用户"当前版本不支持"，而不是静默失败。**
